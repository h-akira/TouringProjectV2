# 0015. 記録の持ち主を Room に持たせ、設定の名前と食い違うあいだは送らない

- 日付: 2026-10-30
- 状態: 採用

## 背景

端末の記録（Room）が、どのユーザー名のものかを、Room 自身は知らない。送信は、送る瞬間の設定のユーザー名で Backend の窓口を作る。名前は画面の設定の塊（`Settings`）の1項目で、画面が持つ古い写しを丸ごと書き戻す形で更新される。このため、記録と名前の食い違いが、次のどの経路でも起き、それを検知する比較がどこにもない（全体レビュー R10-03・R2-01・R2-02）。

- 設定を読めなかった起動で、乱数の名前が作られて保存され、本当の名前と設定が上書きされる（R2-01）
- 名前の変更が、記録を入れられず、戻す保存も失敗して終わった（`Mismatched`）あとも、送信が走る（R2-02）
- 名前の保存・戻しと、ほかの設定の画面の古い写しの書き戻しが前後する（R10-03）

起きると、端末の記録が別のユーザー名で Backend に送られる。前の名前は端末から消えるので、利用者が控えていなければ戻せない。

## 選択肢

1. Room に記録の持ち主を1行持たせ、設定の名前と合うときだけ送る。合わなければ止めて知らせる
2. 1に加えて、食い違いを見つけたら、設定の名前を持ち主の名前に自動で書き戻す
3. 1に加えて、SC-18 に「この端末の記録の名前に戻す」ボタンを足す
4. 持ち主を持たず、個々の経路（読めなかった起動・`Mismatched`・古い写し）だけを塞ぐ

## 決定

1にする。持ち主は Room の `owner`（1行）に置き、記録を入れ替える書き込み（名前の変更）と同じトランザクションで書き換える。送信の回は、設定の名前が持ち主のときだけ走る。合わないあいだは何も送らず、SC-14 と SC-18 に知らせる。

- 持ち主の行が無い端末（この版へ更新した端末）は、最初の送信の回で、そのときの設定の名前を持ち主にする。設定を読めなかった起動で名前が未確定のあいだは、持ち主にしない。
- 食い違いを直す手段は、既存の SC-18（名前を選び直す）にする。持ち主の名前へ戻すときは、記録を入れ替えず、クラウドの記録を足すだけにし、未送信があっても止めない。そうしないと、食い違いのあいだは送れず、未送信があるので名前も変えられず、行き止まりになる。ほかの名前へ変えるときは、今までどおり未送信で止める。
- 設定を読めなかった起動では、名前を作って保存せず、更新も書かない。名前が確定するのは、設定が空だった（初めての起動）ときと、利用者が名前を選んだときだけ。
- 設定の更新は、画面の古い写しではなく、画面が変えた項目だけを最新の設定に重ねる。ユーザー名は名前の変更でしか変わらない。

2にしないのは、持ち主の名前が正しいとは限らない（利用者が意図して変えた名前を、戻す保存の失敗が原因だと決めつけて消しうる）ため。3は画面が増え、4は新しい経路が出るたびに塞ぎ直しになる。

## 影響

- Room のスキーマが 6 → 7 になる（表を足すだけの Migration）。
- 食い違ったとき、利用者は SC-14・SC-18 で知らされ、SC-18 で名前を選び直すまで記録は送られない。送られない間も端末の記録は失われない。
- 「未送信」の SQL（`store/Unsent.kt`）と「名前の変更を止める条件」（`nameChangeBlock`）は、同じ変更でそれぞれ1か所にまとめる。
- 更新前から食い違っていた端末は、最初の送信の回で現在の設定の名前が持ち主になるので、検知できない。
