# 0009. 削除はクラウドにも跡を残し、跡のある記録への置き直しを断る

- 日付: 2026-10-21
- 状態: 採用

## 背景

スライス3で、会話・地点メモ・走行の削除と、メモ・地点メモの書き足しを、端末からクラウドへ送る（US-C-05.006 の送る側）。スライス2では、端末が走行のメタ情報とルートのかたまりを「最新の全体を置く。同じ識別子は1つにまとまる」形で送り、Backend は `updatedAt` が新しいときだけ上書きしていた。

削除を足すと、次の場面が起きうる。

- 端末で消した記録の古い版が、送信の回の途中や、送れずに溜まっていた分として、削除のあとに Backend に届く。そのまま置くと、消した記録が戻る
- 次のスライスでは、別の端末への引き継ぎと端末をまたいだ同期を行う。別の端末が、消された記録をまだ持っていて送り返すことがある

05 §9 の「同期のしかた」は、どちらの変更を優先するかと、削除の伝え方を未決にしていた。

## 選択肢

1. 記録ごとに `PUT`（最新の全体）と `DELETE` を送り、端末に削除の印を溜める。クラウドは記録を消すだけで、跡を残さない
2. 1に加えて、クラウドにも削除の跡を残し、跡のある記録への `PUT` を断る
3. 変更をまとめて送る受け口を1つ作る（`POST /sync` に変更の一覧を送る）

## 決定

2を採る。

- `DELETE` を受けると、Backend は先に削除の跡（`DELETED#<種類>#<id>`）を書き、それから記録を消す。記録が無くても跡を書く。何度呼んでも 204
- 跡のある記録と、跡のある走行の下の記録への `PUT` は、書かずに 410 を返す。Android は 410 を送れたものと同じに扱い、送り直さない
- 跡には期限を付けない
- 端末では、記録を消すのと同じトランザクションで削除の印を書き、送れたら印を消す

1をやめたのは、古い送信で消した記録が戻る場面を、端末の送る順番だけでは防ぎきれず、次のスライスの端末をまたぐ同期で必ず跡が要るため。今のうちに跡を残しておけば、次のスライスで、スライス3のあいだに消した分も伝えられる。

3をやめたのは、スライス2の受け口（走行の `PUT`・ルートのかたまりの `PUT`）を作り直すことになり、手戻りが最も大きいため。

## 影響

- 05 §9 の「同期のしかた」のうち、削除の伝え方はこれで決まる。どちらの変更を優先するか（端末をまたいだ突き合わせ）は、次のスライスで決める
- DynamoDB に、消した記録の数だけ小さな跡が残り続ける。1人の記録の数では問題にならない
- 07 の UC-7 に、削除の跡と 410 を書く（スライス3の Backend の plan）
- 消した記録の識別子を、同じユーザー名でもう一度使うことはできない。識別子は端末と Backend が UUID で作るので、ふつうは起きない
