# 0014. 質問にかけてよい時間は、受け付けから決めた締め切りで Backend と Agent が打ち切る

- 日付: 2026-10-29
- 状態: 採用

## 背景

1つの質問にかけてよい時間が、ユニットごとに別々に決まっている。

| 場所 | 今の上限 |
|---|---|
| Android | 受け付けの応答が返ってから120秒で回答を待ち切り、「時間切れです」を出す |
| worker（Backend） | Lambda の実行は120秒。SQS で待った時間と文字起こしの時間を含む |
| Backend から Agent への読み | 1回の読みごとに90秒。全体の上限ではない |
| Agent | 上限なし（周回の上限8・ツールの上限4だけ） |

07 UC-5 は「打ち切りや取り消しの後も、Backend の処理は続いてよい」とだけ書き、どこで誰が打ち切るかを約束していない。この結果、次の3つが別々に起きうる。

- worker が時間切れで落ちると、記録が `processing` のまま残る（全体レビューの R4-02。メモリ切れの落ちも同じ形だが、そちらは別に直す）
- Agent が打ち切られずに動き続け、利用者が聞かない回答のために LLM を使い、その往復を履歴に残す（R5-02）
- 取り消しや120秒の時間切れのあとに言い直すと、同じ会話への呼び出しが重なり、後に終わったほうが先の往復を履歴から消す（R12-01。Agent #6 を閉じたときの「回答待ちのあいだは次の質問を始めない」という前提が、Android の取り消しと時間切れでは成り立たない）

個々に直すと、それぞれが別の秒数を選び、また噛み合わなくなる。

## 選択肢

1. 受け付けで締め切りを決め、上流から下流へ渡す。Backend と Agent はその締め切りで打ち切る
2. ユニットごとに上限を足す。秒数は各ユニットが決める
3. 今のまま。Android が待ち切ったら、Backend と Agent の処理は続けさせる

## 決定

1を選ぶ。

- Backend が受け付けで `deadline = 受け付けの時刻 + 110秒` を決め、質問の記録に残す。Android の120秒より10秒早い
- worker は、`deadline` と Lambda の残り時間の早いほうを予算にし、文字起こしと Agent の呼び出しを残りの時間で包む。予算が尽きたら、記録を `failed`（`agent_failed`）で終える。理由（`timeout`）はログに残す。07a の `error` の列挙と Android は変えない
- Backend は Agent への本文に `deadlineSeconds`（`deadline` から合成の余白10秒を引いた残りの秒数）を足す。Agent はその時間で呼び出しを打ち切り、履歴を残さずに `error` を返す。Backend の読みの時間切れは、Agent の締め切りより長くして、Agent の `error` を読めるようにする
- Agent は `session_id` ごとの錠の中で、履歴の読みから書き戻しまでを行う。取り消しの経路で呼び出しが重なっても、先の往復が消えない
- 秒数は `lib/budget.py` の定数に置く。Android の120秒がコードに固定されていて、片方だけ変えても噛み合わないため、SSM のパラメーターにはしない

2をとらないのは、秒数がユニットごとに決まると、また噛み合わなくなるため。3をとらないのは、聞かれない回答のために LLM の費用がかかり、履歴にも残るため。

## 影響

- 07 UC-5 の「Android があきらめても処理は続いてよい」をやめる。07 UC-8 に `deadlineSeconds` を足し、Agent は Backend の読みの時間切れより先に打ち切る
- 時間切れは、Android では「AI が答えられませんでした」と読み上げられる。Android が120秒で待ち切ったときの「時間切れです」とは文言が違う
- 110秒を超える質問（Web 検索が遅いときなど）は、Android が待ち切る前に失敗として返る。Android の待ちは120秒のままなので、利用者が待つ時間は短くなる
- worker が落ちる別の形（メモリ切れ・実行環境の落ち）は、この決定では閉じない。受け持ちの時刻（`claimedAt`）で別に扱う（スライス6の plan 6）
- Agent #6 を再び開き、この plan で閉じる

## 追記（2026-10-30、実機の確認）

Agent の smoke で、同じセッションに 2 本を並べて送ると、AgentCore Runtime が 2 本目を 502（`RuntimeClientError`）で断ることを確かめた。2 本目の質問は Agent のログにも届いていない。1 本目は正常に答え、履歴も壊れない。

- R12-01 の「後に終わったほうが先の往復を消す」は、実機では Runtime が先に防ぐ。Agent の錠は、念のための二重の守りとして残す
- 断られた質問は、Backend が試し直さずに `agent_failed` で終える（試し直すのは `RetryableConflictException` だけ）。言い直しが前の質問の途中に当たると失敗になるが、この決定の前から同じ

## 追記（2026-10-30、デプロイ後の smoke で分かったこと）

実機で、同じセッションの同時の呼び出しは、Runtime が断ることもあるが、別のインスタンスで動かすこともあると分かった（ログのストリームが別。デプロイ後の smoke で確認）。履歴はプロセスの中にあるので、そのあとの呼び出しは、自分が着いたインスタンスの履歴しか見られず、片方の往復が履歴から抜ける。セッションごとの錠が1本ずつにするのは、同じインスタンスに着いた呼び出しに限る。

影響は、取り消しやあきらめのあとの言い直しが、別のインスタンスに着いたときに、前の往復を知らないこと。Agent の issue に残した。
