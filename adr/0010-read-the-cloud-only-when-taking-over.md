# 0010. クラウドの記録は引き継ぎのときだけ読み、新しいほうを勝たせて突き合わせる

- 日付: 2026-10-22
- 状態: 採用

## 背景

スライス2・3では、端末の記録（Room）が正で、端末はクラウドへ送るだけだった。Backend は `updatedAt` が新しいときだけ上書きし、削除は跡を残して、跡のある記録への置き直しを 410 で断る（adr/0009）。クラウドから端末へ読む道は無かった。

要件には、別の端末や入れ直したあとに、同じユーザー名を設定すれば記録が戻ること（US-C-05.004）と、ユーザー名を変えるとその名前の記録に切り替わること（US-E-06.004・.005）がある。05 §9 には「端末とクラウドの記録の突き合わせ方（どちらの変更を優先するか）」が未確定として残っていた。

使い方の前提は、1人が1台の端末で使い、ときどき機種を変えるか入れ直す、というもの。2台を並べて同時に使う場面は、要件に無い。

## 選択肢

読む時機:

1. 引き継ぎのとき（ユーザー名を変えるとき）と、利用者が手動で読み直すときだけ読む
2. 1に加えて、アプリが前面に来るたびに前回からの差分を読み、2台を同時に使っても揃える
3. 読み込みは作らず、引き継ぎを後のスライスに回す

読み方:

- a. ユーザーのパーティションを全部、ページ送りで読む受け口を1つ足す（`GET /records`）
- b. 種類ごとの受け口（走行の一覧・走行ごとのルート・質問の一覧など）を足す
- c. Backend が S3 に書き出したものを、端末が落とす

突き合わせ:

- i. `updatedAt` が新しいほうを勝たせ、クラウドに削除の跡があれば端末から消す
- ii. いつもクラウドを勝たせる
- iii. いつも端末を勝たせる

## 決定

1・a・i を選ぶ。

- 読むのは、SC-18 でユーザー名を変えるときと、SC-14 の「クラウドから読み直す」だけ。名前を変えるときは、端末の記録を消してから新しい名前の記録を入れる。今の名前のまま読み直すときは、端末の記録を消さずに突き合わせる
- `GET /records` は、`USER#<ユーザー名>` のパーティションをソートキーの順に強い一貫性で問い合わせ、`cursor` でページを送る。端末は最後のページまで読んでから、1つのトランザクションで入れる
- 同じ記録が両方にあれば `updatedAt` が新しいほうを残す。クラウドに削除の跡があれば端末から消す。端末にだけある未送信の記録は残して送る

理由:

- 2 は、2台を同時に使う場面が要件に無いのに、差分の読み出し（変わった記録を時刻で引く索引か、変更の記録）と、確かめる場面が大きく増える。1 で要件（入れ直しと機種変更・ユーザー名の切り替え）を満たせる
- 3 は、要件の Must に近い引き継ぎが、次のスライスの SC-01 まで実機で確かめられないまま残る
- a は、読む時機が限られるので全部読む重さを許せ、受け口が1つで済む。`RIDE#` の頭にルートのかたまりと地点メモが混ざることも、全部読むので問題にならない。b は前面に来るたびに読む形に広げやすいが、今の範囲には受け口と決めごとが多すぎる。c は書き出しの待ちと後片付けの仕組みが増える
- i は、クラウドの「新しいときだけ上書き」と同じ決まりなので、送るときと読むときで考え方が揃う。削除の跡（adr/0009）を、端末をまたいで削除を伝えるのにそのまま使える。ii は送れていない端末の変更を失い、iii は入れ直す前に送った変更を戻せない

## 影響

- Backend に `GET /records` が増える。`cursor` の中のパーティションキーは使わず、`x-user-name` から作り直す（他人のパーティションを読ませない）
- 端末は、読み込んだ版を送り済みとして入れる。記録中のままクラウドにある走行は、終えた走行として入れて送り直す（サービスの動いていない記録中の走行を作らない）
- SC-18 は、未送信があるときと走行の記録中は名前を変えさせない（US-E-06.008）
- 2台を同時に使うと、一方の変更はもう一方で読み直すまで届かない。両方で同じ記録を変えたときは、読み直した時点で新しいほうが勝つ。2台の同時利用が要るようになったら、選択肢2を考え直す
- 次のスライスの SC-01 の引き継ぎの入口は、同じ読み込みを呼ぶ
