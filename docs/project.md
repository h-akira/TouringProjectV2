# project

## スライス

**スライスとは**: プロジェクト（App・Backend・Agent・CICD の4ユニット）を一度には作れないので、利用者に見える一続きの機能を、全ユニットに縦に通す単位で切る。スライスごとに「仕様（`docs/specs/`）→ 実装計画（`docs/plans/`。ユニットごとなどに分ける）→ 実装 → 実機の確認」を回す。

### スライス1: 土台と、質問の一巡（進行中）

- **目的**: インカムのボタンで質問してから、回答の読み上げを聞き、ナビへ戻るまでを全ユニットに通す。最も大きなリスク（ハンズフリーの起動・インカムのマイクの経路・背面での動作・応答の待ち時間・費用）を、早く実機で確かめるため。
- **範囲の要点**:
  - 質問の一巡
  - 現在地・住所・進行方位の確定
  - Web 検索と周辺検索での回答
  - 15分の会話の文脈
  - 回答の音量
  - 録音の確認
  - 最小限の画面
  - 質問と回答のクラウドへの記録と、段ごとの時間とトークン数の計測
  - 詳しくは[仕様](specs/2026-10-16-slice1-design.md) §2。
- **完了の判定**: 仕様 §1 の成功の判定（走りながらの通し・「右手の〜」が正しい・周辺の施設を向きと距離で答える・失敗が音で分かる・時間とトークン数を集計できる・15分の文脈）。

## 次にやること

1. 計画4b の範囲を決める（`superpowers:brainstorming`）。決めることは3つ。
   - App の issue #1〜#8 のどれを入れるか
   - #7（メディアの音量が低いと聞こえない。ナビの案内も同じ音量を使う）の直し方
   - #8（走行用に JS を組み込んだビルド）の作り方
2. 決めたことを仕様に書き足し、計画4b を書いて実装する。
3. 完了の判定の確認をする。

後回しにした点は、各ユニットのリポジトリの GitHub issue にある。

## 進め方

- 範囲を決めるときは `superpowers:brainstorming`、計画は `superpowers:writing-plans`。計画のコードは、使い捨てのフォルダに展開して、テストとビルドが通ることを確かめてから渡す。
- 実行の方法は利用者が選ぶ（これまでは Native の `superpowers:executing-plans`）。最後に、最も能力の高いモデルで、ブランチ全体のレビューを1回受ける。レビューで見送った小さな点は issue にする。
- ブランチは計画ごとに切る。マージはユニット → 親の順で、親は submodule の指す先を進める。
- コミット・push・デプロイは、利用者の許可を得てから。push の前に `pre-push-secret-scan` をかけて報告する。

## 決まっている前提（ほかの文書に無いもの）

- LLM の入力のトークンを増やす設計は避ける。調整できる値は SSM のパラメーターにする。
- AWS はほかのプロジェクトと同じアカウント。名前に `trv2` を付けて重複を避ける。profile は `touring`（いつも使えるとは限らない。使えないときは利用者に聞く）。
- 接続キー・API の URL・アカウント ID を、コードや文書に書かない。
