## 総評

- **弱いのは「並行と後始末」と「文書の追従」。** 不具合（A）は、取り消し・背面・時間切れのあとに古い処理の後始末が新しい処理の資源を壊す、またはつながりが外れない、という形に集まった（R3-01・R1-01・R1-03・R4-02・R5-02・R12-01）。文書（D）は件数が最も多いが、ほとんどが Low で、モックの文言の古さと、04・03 と実装の小さな食い違い。
- **構成（S）は、小さな部品の切り方は良く、ユニットをまたぐ決まりの置き場所が弱い。** 時間の予算・「未送信」の条件・方位の名前の付け方・「最初に受けた値を残す」手順など、同じ決まりが複数の場所に別々に書かれ、すでにずれ始めている。CICD を足す前に、環境の名前の焼き込みと手作業の受け渡し（R11-02〜R11-05）を片付けておくのがよい。
- **費用（E）は LLM が大半。** ポーリング・Lambda・DynamoDB の費用は LLM の1%に満たない目安で、詰める価値は小さい（R11-20）。プロンプトのキャッシュ（R5-03）など、モデルを変えずに下げる手がある。

## 方法

1. **機械の検査**（下の「機械の検査の結果」）。
2. **範囲ごとのレビュー**: Android を3つ（質問と音・記録と同期・画面と組み立て）、Backend、Agent、文書を2つ（要件の層・方針と設計の層）に分けて読んだ。
3. **横断のレビュー**: ユニット間の契約、セキュリティ、Android の構成、Backend・Agent とユニット間の構成、GitHub issue。
4. **検証**: High の指摘（当初3件）を、書いた側とは別に読み直して反証を探し、まとめ役も自分でコードを読んで確かめた。その結果、R3-01 は High のまま、R10-01・R11-01 は Medium に下げ、関連の R1-03 は Low に下げた。誤りと分かった部分は本文を直した。Medium 以下は検証していないので、確度は書いた側の判断。
5. **統合**: 同じ根の指摘をまとめ（5組）、行番号を機械で突き合わせて誤りを直した。

レビューの前に利用者と決めたこと:

- 指摘は報告だけにする（issue に起こすかは、報告を読んでから決める）。
- 費用（E）は Backend・Agent・ユニット間の構成のレビューの観点に入れる。テストの抜けは不具合（A）の一部として扱う。
- モックと画面の食い違いは文書の整合（D）に含め、重大度の上限を設けない。食い違ったときは**原則として実機（実装）を正とし、モックを直す案にする**。ただし個別に判断する（この原則が `docs/` に書かれていないことは R7-01）。
- 構成（S）では、採用した ADR の決定そのものも疑ってよい（その場合の対応案は、新しい ADR で置き換える提案）。結果として、ADR の決定を覆す提案は無かった。

## 書式

各指摘は `### <ID> [観点] [重大度] [確度] 題` と、場所・内容・起きる条件・影響・対応案（・関わる文書・同じ根）。そのまま issue に写せる形にしてある。

- **ID**（`R4-02` など）は、この報告の中で指摘を指すための名前。数字の前半はレビューの範囲、後半は範囲の中の番号で、まとめて消した番号は欠番になる。
- **観点**: A 不具合（テストの抜けを含む）・B 脆弱性・C 細部の読みやすさ・D 文書の整合・E 費用・S 構成・I issue。
- **重大度**: Critical（記録が失われる・他人のデータに触れる・秘密が漏れる・走行中に使えなくなる）、High（普通の使い方で利用者に見える誤動作／文書と実装の食い違いで誤る）、Medium（条件の限られる不具合・次の改修で踏みやすい作り）、Low（小さな不具合・読みにくさ・文書の小さなずれ）、Info（好み・提案）。S では High＝その作りのせいで不具合がすでに出ている、Medium＝次の機能を足すときの手戻り、と読み替えた。
- **確度**: `[確か]` はコードで経路を追えたもの、`[ありうる]` は条件が揃えば起きるが、揃うか（実機の振る舞い・AWS の中の様子）を確かめきれないもの。

## 構成の総評

詳しくは structure.md。

- Android: パッケージの切り方と、窓口（interface）越しの作り物でテストする作りは良い。問題の根は4つ。共有の資源（音声の経路）に持ち主の印が無いこと、同じ決まり（未送信の条件など）が何か所にもあること、記録の持ち主（ユーザー名）が設定の塊にあること、`AppGraph`・`AppUi` に組み立てとつなぎが集まっていること。記録の種類を1つ足すと、約15か所を直すことになる。
- Backend・Agent: `handlers` と `lib`、Agent の `main` と `handler` の分け方は良い。質問の記録の形が5つのハンドラに散っていること、`lib` から `handlers` への逆向きの依存、環境（dev）の焼き込みが弱い。
- ユニット間: 時間の予算・方位の名前・会話の区切り・質問の派生する値の決め方が、ユニットごとに別々に書かれている。07a（API の正本）を Android のテストは読まず、Backend のテストも応答の形までは確かめていない。
- 直す順の提案（structure.md §2）: (1) 振る舞いを変えない「移すだけ」の作り替え → (2a) ユニットをまたぐ時間の予算（spec を通す）と (2b) Android の音声の経路の札（R1-01・R1-03 を閉じる） → (3) 記録の持ち主と未送信の条件 → (4) CICD のスライスの最初の plan で環境の焼き込みと手作業の受け渡し → (5) 契約を機械で確かめる → (6) 新しい画面を足す前に `AppUi`・`AppGraph` を分ける。

## セキュリティの総評

詳しくは cross-unit.md。

- 認証・認可: 読み書きのキーはすべてユーザー名から作られていて、ユーザー名を知らずに他人の記録へ届く穴は無い。共通の接続キーを持つ人が他人のユーザー名を名乗れることは、文書で割り切っている。ただし割り切りの書き方が「見られる」だけで、「書き換え・削除もできる」とは書かれていない（R9-02）。
- 個人情報: 最も重いのは、Agent のトレースに質問・位置・回答が載ること（R5-01）。Android のマニフェスト・平文通信・接続キーの暗号化・ログに、新しい問題は無い。
- 依存の既知の脆弱性: デプロイされるものでは、ほぼ効かない。外から値を届ける経路が見当たらないものと、手元の CDK の合成でだけ使うものだった（R9-05 と cross-unit.md の総評）。
